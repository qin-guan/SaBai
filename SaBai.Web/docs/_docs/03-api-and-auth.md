The web app no longer owns an API layer. All reads and writes go to the
**SaBai.API** service (a .NET FastEndpoints app) through the generated
**`@sabai/sdk`** client. Authentication is handled by **WorkOS** on the API side;
the API issues its own JWT bearer token which the web app stores and replays.

## 1. Architecture

```
┌────────────────────────────┐        HTTPS + Bearer JWT        ┌──────────────────────────┐
│        SaBai.Web           │  ───────────────────────────────▶ │        SaBai.API         │
│  (Next.js Pages Router)     │                                   │  (FastEndpoints)         │
│                             │  ◀─────────────────────────────── │                          │
│  @tanstack/react-query      │        JSON / ProblemDetails      │  WorkOS  +  Postgres     │
│  + @sabai/sdk hooks         │                                   │  + Qdrant + S3 (rustfs)  │
└────────────────────────────┘                                   └──────────────────────────┘
```

- **Data access**: `@sabai/sdk` (generated by [Kubb](https://kubb.dev/) from the
  API's OpenAPI document).
- **Server state**: `@tanstack/react-query` (`useQuery` / `useMutation`).
- **Auth**: WorkOS verifies credentials; the API mints a JWT returned by
  `POST /auth/login`.
- **Validation**: Zod (forms), plus the generated `@sabai/sdk/zod` schemas.

> Database schema ownership moved to the API (EF Core migrations). The web app
> has no Drizzle/Supabase code and does not connect to Postgres directly.

## 2. Environment variables

The only variable the web app needs:

| Variable              | Description                                            |
| --------------------- | ------------------------------------------------------ |
| `NEXT_PUBLIC_API_URL` | Base URL of SaBai.API (e.g. `http://localhost:5250`).  |

Copy `.env.example` to `.env` and set it. The API allows the web origin via its
CORS policy (`Cors:AllowedOrigins`, defaulting to `http://localhost:3000`).

## 3. Authentication flow

1. The user submits email + password on `/login`.
2. The login page calls the SDK's `POST /auth/login` mutation:
   ```ts
   const result = await login.mutateAsync({ body: { email, password } });
   setToken(result.accessToken, result.expiresAt); // stores the sabai_token cookie
   ```
3. The JWT is stored in the `sabai_token` cookie (`src/lib/api/token.ts`). It is
   intentionally readable from the browser so `@sabai/sdk` can attach it as an
   `Authorization: Bearer …` header.
4. `src/proxy.ts` (Next middleware) gates routes on the cookie's presence and
   redirects unauthenticated users to `/login?redirectTo=…`.
5. If the API rejects a request with `401`, the shared React Query client
   (`src/lib/api/queryClient.ts`) clears the token and redirects to `/login`.

Signing out clears the cookie (`clearToken()`).

## 4. Using the SDK

Every query/mutation is passed the shared `apiConfig` (base URL + bearer token):

```ts
// src/lib/api/config.ts
export const apiConfig = {
  baseURL: env.NEXT_PUBLIC_API_URL,
  auth: () => getToken(),
};
```

### Query

```ts
import { useQuery } from "@tanstack/react-query";
import { saBaiAPIEndpointsPatientsListGetEndpointQueryOptions } from "@sabai/sdk/hooks";
import { apiConfig } from "@/lib/api/config";

const { data } = useQuery(
  saBaiAPIEndpointsPatientsListGetEndpointQueryOptions({}, apiConfig),
);
const patients = data?.patients ?? [];
```

Add options with a spread (e.g. to disable the query until an id is known):

```ts
useQuery({
  ...saBaiAPIEndpointsPatientsGetEndpointQueryOptions({ path: { id } }, apiConfig),
  enabled: !!id,
});
```

### Mutation

```ts
import { useMutation } from "@tanstack/react-query";
import { saBaiAPIEndpointsVisitsCreatePostEndpointMutationOptions } from "@sabai/sdk/hooks";

const createVisit = useMutation(
  saBaiAPIEndpointsVisitsCreatePostEndpointMutationOptions(apiConfig),
);

createVisit.mutate({ body: { patientId, villageCodeId } });
// with a path param: mutate({ path: { id }, body: { ... } })
```

### Invalidation

```ts
import { useQueryClient } from "@tanstack/react-query";
import { saBaiAPIEndpointsConsultsListByVisitGetEndpointQueryKey } from "@sabai/sdk/hooks";

const queryClient = useQueryClient();
queryClient.invalidateQueries({
  queryKey: saBaiAPIEndpointsConsultsListByVisitGetEndpointQueryKey({
    path: { visitId },
  }),
});
```

### Error handling

SDK errors are the API's RFC 7807 ProblemDetails wrapped in a `ResponseError`.
Use the helpers in `src/lib/api/errors.ts`:

```ts
import { getApiErrorMessage, getApiErrorStatus, isUnauthorizedError } from "@/lib/api/errors";

getApiErrorMessage(error, "Failed to save.");
getApiErrorStatus(error); // e.g. 409
```

### Response shapes

- List endpoints that return a wrapper: `patients` → `{ patients: [...] }`,
  `villageCodes` → `{ villageCodes: [...] }`.
- Single-resource GETs return the entity directly.
- Some "read the child of a parent" endpoints (e.g. `GET /visits/{id}/vitals`)
  return **400 when no record exists** rather than `null`; gate them with
  `enabled` and treat an error as "no record yet".
- Enums are lowercase string keys, e.g. `SaBaiAPIDomainGenderKey = "male" | "female"`.

## 5. Regenerating the SDK

`@sabai/sdk` is generated, not hand-written. After changing the API:

```bash
# 1. Run the API (it serves OpenAPI at http://localhost:5250/openapi/v1.json)
#    e.g. `dotnet run --project SaBai.API` or `aspire start`

# 2. Regenerate the client from the live OpenAPI document
pnpm --filter @sabai/sdk generate

# 3. Build the package so SaBai.Web picks up the new types
pnpm --filter @sabai/sdk build
```

- Generation config: `SaBai.Sdk/kubb.config.ts`.
- Generated output: `SaBai.Sdk/src/gen` (do not edit by hand) and `SaBai.Sdk/dist`.

## 6. Patient photos & face search

Patients have a single profile photo (stored in the RustFS bucket, like clinical
files) and any number of enrolled faces (stored as vectors in Qdrant, using the
same face-recognition pipeline as the generic `/persons` endpoints).

Patient endpoints:

| Method + route | Purpose |
| -------------- | ------- |
| `PUT /patients/{id}/photo` | Upload/replace the profile photo (multipart, `image`). |
| `GET /patients/{id}/photo` | Download the profile photo (binary). |
| `DELETE /patients/{id}/photo` | Remove the profile photo. |
| `POST /patients/{id}/faces` | Enroll a face photo for the patient. |
| `GET /patients/{id}/faces` | List the patient's enrolled faces. |
| `DELETE /patients/{id}/faces/{faceId}` | Delete one enrolled face. |
| `POST /patients/search-by-face` | Find patients by face photo (multipart `image`, optional `threshold`/`maxMatches`). Returns matches with similarity. |

Patient DTOs include `hasPhoto` and `hasFace` flags. Faces are namespaced in the
face store as `patient:{id}`, so they never collide with `/persons` identities.

On the web side:

- `src/lib/api/patientPhoto.ts` fetches the authenticated photo blob and exposes
  it as an object URL (`usePatientPhoto`); `<PatientPhoto patientId hasPhoto />`
  renders it (or a default image).
- `src/lib/api/patientEnrollment.ts` uploads a photo and enrolls a face from a
  captured data URL.
- Registration stores the captured photo + face after creating the patient, the
  edit form can replace them, and the scan-face page searches by face
  (`POST /patients/search-by-face`) and opens a visit for the chosen match.
